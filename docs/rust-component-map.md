# Rust component feasibility and boundaries

This inventory distinguishes the independently authored RHSO helper from the programs it inspects or configures. It is based on previously acquired code and derived reports, not a new device investigation. Decompilation recovers partial program structure and behavior; it does not recover original source or a reproducible build.

| Component | Existing evidence | Rust work feasible within this module | Boundary and remaining dependency |
|---|---|---|---|
| RHSO backend | Independently authored Go validation, plans, backups, journals, diagnostics, API staging, stack adapters and tests | Port its implementation and meaningful synthetic tests to Rust; build a native Android executable and retain the external CLI/JSON contract | Filesystem metadata, SELinux, durability, TLS, crypto and Android runtime behavior require platform validation. A Rust source port alone does not establish a working native release. |
| RHSO WebUI and launcher | Independently authored UI and inspected KernelSU bridge contracts | Candidate Rust/WASM controller preserves UI policy/workflows behind thin JavaScript loading and bridge adapters; native and mock-browser checks passed | HTML/CSS, generated glue and the existing KernelSU SDK remain interoperability dependencies. Installed Android WebUI host compatibility still requires actual host verification. |
| TrickyStore 1.4.1 | Installed Java/DEX service, native ARM64 library, static parser/reload findings and code pins | Continue independent Rust keybox validation and guarded three-file management while retaining the existing engine | Rust helper code does not replace the attestation engine, KeyMint/TEE or hardware. Decompiled proprietary/obfuscated bytes cannot be treated as maintainable Rust source. No engine replacement is delivered. |
| HMA OSS installed schema 93 | Installed manager/module DEX and native program pins; private Binder manager contract; blacklist/opposite-list semantics | Fixed-resource additive selected-scope configuration adapter with exact backups, stale guards and semantic preservation of unknown fields | External config write has no proven immediate Binder activation. Apply and rollback require manual reboot and fresh runtime checks. Replacing HMA would require its actual upstream source, license review and Android integration tests. |
| BreZygisk build 548 | Installed JavaScript marker setter and bounded native decompilation; cached mount-namespace behavior | Explicit fixed persistent-marker intent adapter with exact metadata/absence restoration | Native namespace/zygote machinery remains external. Marker readback does not prove namespace adoption or compatibility with other modules. No automatic process control or native replacement is delivered. |
| PIF v18 | Installed shell/action code and previously inspected manual action behavior | Keep diagnostics and protected-state binding; a separately scoped port could reproduce only independently verified behaviors | Its original action can refresh remote configuration and affect GMS. Those effects are not implied by backend language migration; spoof flags and existing engine state remain protected. |
| CleveresTricky 2.8.7 | Installed Java/DEX client contract and native format boundary | Independently implement a bounded configured HTTPS raw-XML staging adapter | Exact supplied provider contract remains unavailable. | Specter | Read-only pinned public GPL-3 source and schema/template analysis | Use factual configuration contracts to design independent narrow adapters | Original scripts/templates are not incorporated into the MIT helper. Broad cleanup/fanout behaviors lack the helper's recovery contract. ZygiskNext configuration does not establish BreZygisk compatibility. |
| WildKernels kernel / Android kernel | Acquired ARM64 image, release identity, symbol/static analysis and limited pseudocode | Kernel metadata diagnostics and independently written bounded inspections | Linux/OEM kernel source, configuration, toolchain, licenses and device-specific build/boot compatibility are prerequisites to any kernel change. Kernel Rust support does not translate an existing C/native image into a Rust kernel. Boot image and unlocked state are outside this rewrite. |
| Android framework/services/NFC | Copied program code and targeted static analysis | Call existing supported Android services for bounded diagnostics; retain scoped output | OEM system source/build/signatures/SELinux/ABI and hardware integration are separate dependencies. | Signed DroidGuard runners | Two copied signed program APKs verified against the production loader pin; bounded wrapper/RuntimeApi analysis | Preserve the evidence boundary and report what is known | Signed bytes establish program-signing provenance only. Native VM inputs/signals, the active challenge/program and server acceptance are not recovered. No VM execution, hook, patch or replacement is delivered. |

The stack port retains two fixed resources, `hma-config` and `brezygisk-unmount`, with a separate journal and private full backups under the common operation lock. Protected TrickyStore backups are verified and associated before an active stack Apply or explicit rollback; stack rollback restores only its selected resource. Preview and readback remain redacted, and both directions report manual reboot required and runtime adoption unknown. This is a configuration management capability, not proof that root traces disappear or Wallet accepts the device.

The optional public trust/revocation checks remain distinct from private-import policy, hardware evidence, integrity verdicts and payment acceptance. A change of implementation language must preserve those distinctions, fail-closed recovery and untrusted-input limits. Packaging and release may claim Rust-native backend only after the actual build artifact and platform tests verify that claim.

The initial Windows Rust stack/reset port was verified with `cargo test -p rhso-backend --test stack_transactions --test reset_protocol --lib`: 20 stack integration tests, 8 reset integration tests and 4 reset unit tests passed. Tests use temporary fake-engine fixtures and inert scripts. The independently testable clear-step ledger checks durable attempted-step records before synthetic callbacks; the public fake App never dispatches destructive commands. Unknown HMA fields and large numeric values are preserved, old schema-1 journals/nullable marker selection arrays remain readable, and interrupted or corrupt state stays blocked. These results do not certify Android ownership/SELinux/durability, runtime activation, VM behavior or payment acceptance. Full workspace checks and the actual Android release build are separate gates.
